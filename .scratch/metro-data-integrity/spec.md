# Spec: 地鐵資料真實性與跨線轉乘修正

Status: ready-for-agent

前置文件：`METRO_TRANSFER_AND_INTEGRITY_AUDIT.md`（稽核報告，先於本 spec 產出，提供逐線隱藏清單）
相關文件：`METRO_DATA_SOURCE_AUDIT.md`（外部資料源可用性評估，不同問題）

---

## Problem Statement

使用者打開 TransitRail 查地鐵，會遇到三種都很糟的狀況，而且**無法分辨自己遇到的是哪一種**：

1. **看到假資料，而且介面聲稱它是真的。** 查倫敦地鐵 8 月 5 日的班次，看到三班車，全部標記為即時（`realtime: true`）。實際上那三筆是 8 月 1 日早上九點半抓的當下實況，被貼上七個不同日期。查新加坡或曼谷，看到一整天 109 班車，每班車程一模一樣、票價一模一樣——那是用固定班距公式生成的，不是任何業者的班表。

2. **明明選得下去，按了卻查無資料。** 車站選單列出首爾 279 個地鐵站，但選了江南（2 號線）再選首爾站（1／4 號線），結果是空的——因為跨線轉乘完全沒有實作。使用者不會知道問題出在轉乘，只會覺得這個 App 壞了。

3. **在最常查的那天反而查不到。** 香港港鐵今天只有 4 筆班次，涵蓋 15:27–15:35 這八分鐘；早上或晚上查中環到荃灣，一片空白。而未來六天卻有完整的 378 筆——因為 live 抓到的「下班車」把當天的 curated 全日班表覆蓋掉了。

貫穿三者的是同一個根本問題：**這個產品分不清「我有真實資料」與「我有長得像資料的東西」，於是把兩者用同一種方式呈現給使用者。** 而在交通工具這個領域，照著錯的發車時間出門的代價是錯過班車。

## Solution

建立**單一的「什麼算真實資料」判定標準**，讓它同時決定三件事：哪些路線與車站出現在選單、哪些日期可以查、以及搜尋結果怎麼呈現。

使用者感受到的改變：

- **按得下去的組合，一定查得到結果。** 選單會依起點與日期動態收斂——選了江南之後，終點選單只剩從江南真的搭得到的站。再也不會出現「選得下去卻查無資料」。
- **選單裡的路線，背後都有真實資料。** 沒有可驗證班表的路線與車站不再出現。新加坡、曼谷、東京地鐵、以及中／德／法／比／挪／瑞／馬的地鐵會從選單消失。這是刻意的取捨：**寧可誠實地少，不要熱鬧地假。**
- **只有真的知道未來班次的網路才提供未來日期。** 首爾與波士頓保留七天查詢（它們的資料按服務日分型，跨日合法有效）；倫敦與香港只能查當天，因為它們的資料只有當下這一刻是真的。
- **跨線轉乘真的會動。** 首爾九條線之間的換乘可以查，而不是只有同一班車經過的站對。

## User Stories

1. 作為查詢地鐵的使用者，我希望選單裡出現的每一個車站背後都有真實班表，這樣我才不會浪費時間在查不到結果的組合上。
2. 作為查詢地鐵的使用者，我希望選定起點之後，終點選單只列出從該起點真的搭得到的車站，這樣我按下查詢一定有結果。
3. 作為查詢地鐵的使用者，我希望終點選單會依照我選的日期調整，因為平日與週末的可達範圍不同。
4. 作為查詢地鐵的使用者，我希望當某個網路只有當天資料時，日期選擇器就只讓我選當天，而不是讓我選了未來日期再給我假資料。
5. 作為首爾地鐵的使用者，我希望能查江南到首爾站這種跨線行程，因為那是最基本的地鐵查詢需求。
6. 作為首爾地鐵的使用者，我希望跨線行程顯示換乘站與換乘等待時間，這樣我知道要在哪裡下車、大概等多久。
7. 作為首爾地鐵的使用者，我希望轉乘結果會依照我查詢日期的服務日類型（平日／週六／週日假日）給出正確班次。
8. 作為首爾地鐵的使用者，我希望換乘等待時間反映真實的站內步行時間，而不是一個可能只有兩分鐘的理論值。
9. 作為波士頓 MBTA 的使用者，我希望看到完整一天的班次而不是被截斷在下午五點，這樣我晚上也能用。
10. 作為波士頓 MBTA 的使用者，我希望週六的班次不會因為重複累積而出現大量重複列。
11. 作為倫敦地鐵的使用者，我希望查當天班次時看到的是真的即時資料，並且清楚標示它是即時的。
12. 作為倫敦地鐵的使用者，我不希望在未來日期看到被複製過去的舊資料，寧可看到「此網路僅提供當天查詢」的明確說明。
13. 作為香港港鐵的使用者，我希望在任何時段查詢都能得到結果，而不是只有下午三點半那八分鐘。
14. 作為新加坡或曼谷的使用者，我希望在該地區沒有可驗證班表時被明確告知，並拿到官方查詢管道，而不是拿到一份看起來很完整但是生成出來的假班表。
15. 作為使用者，我希望介面上標記為「即時」的資料真的是即時的，因為那個標記會直接影響我要不要衝去月台。
16. 作為使用者，我希望在只有班距資訊、沒有逐班時刻的情況下，App 顯示的是服務時段與班距，而不是編造出來的發車時間。
17. 作為使用者，我希望 App 內看到的資料誠信標示與 Google 搜尋結果頁看到的一致，不要一邊誠實一邊灌水。
18. 作為使用者，我希望轉乘行程的票價計算正確——單一路網內的轉乘不應該被收兩次費。
19. 作為使用者，我希望反向查詢（例如荃灣到中環）給出的時刻是真的反向班表，或者明確標示它是推算的。
20. 作為使用者，我希望跨線轉乘能在真實的換乘站發生（例如港鐵荔景），而不是只能在路線檔剛好的起訖點換乘。
21. 作為使用者，我希望當我查的路線在該日期沒有資料時，得到的訊息說明**為什麼**沒有（無此路線／該網路僅供當天查詢／該區無可驗證班表），而不是一個空白畫面。
22. 作為維護者，我希望「什麼算真實資料」只有一份定義，這樣 SEO 頁與 App 不會各說各話。
23. 作為維護者，我希望這份定義是純函式且有測試，這樣我改動判定規則時能立刻知道哪些路線的可見性會變。
24. 作為維護者，我希望能執行一個腳本，列出目前每個路線檔的真實性分類，這樣每日爬取之後我能看出資料品質有沒有退化。
25. 作為維護者，我希望當 live provider 只回傳幾筆「下班車」時，不要覆蓋掉當天既有的完整班表。
26. 作為維護者，我希望 scraper 不要把單一時刻的即時快照寫進未來日期，因為那從定義上就不可能是真的。
27. 作為維護者，我希望 LLM 產生的轉乘資料要嘛不寫入 committed 資料，要嘛帶有明確標記，這樣它永遠不會被誤認為實測資料。
28. 作為維護者，我希望隱藏規則的變更不會靜默地讓已上線的 SEO 路線頁變成 404，該補的 301 要有明確流程。
29. 作為維護者，我希望知道每個地鐵網路在 repo 裡的覆蓋狀態，這樣我能決定下一個要接的資料源。
30. 作為維護者，我希望新增一個 provider 時，資料真實性的判定會自動套用，而不需要在三個地方各加一次規則。
31. 作為使用者，我希望路線圖上顯示的線都是有班表資料的線，不要看到一條只存了兩個站的「銀座線」。
32. 作為使用者，我希望在被隱藏的地區，看到的是有用的替代方案（業者官方連結），而不是一個死掉的空選單。

## Implementation Decisions

### 一、真實性判定器（新模組，唯一新增接縫）

`scripts/lib/routePages.ts` 的 `isIndicativeTimetable(source, results)` 已經編碼了正確的判定（source 字串比對 `curated|snapshot`，加上「所有班距完全相同」作為 backstop）。它目前只服務 SEO 預渲染頁。

**決定：升格為 `src/data/` 下的資料真實性判定器，成為全系統唯一的定義來源。** `scripts/lib/routePages.ts` 改為 import 它，SEO 頁的既有行為不得改變。

判定器的輸入是一個路線快照（`ScrapedRouteData`）與一個查詢日期，輸出是該日期那一份切片的分類：

| 分類 | 意義 | 呈現方式 |
| --- | --- | --- |
| `scraped` | 從業者或官方來源實際取得的排班／時刻 | 逐班時刻，可宣稱首末班 |
| `realtime` | 抓取當下的即時到離站，僅對抓取當天有效 | 逐班時刻，標示即時，限當天 |
| `indicative` | curated snapshot：代表性服務型態、固定班距 | 服務時段＋班距，不得宣稱逐班時刻 |
| `stale_realtime` | 即時快照被寫進非抓取日期 | 視為無資料 |
| `none` | 該日期無任何列 | 無資料 |

`stale_realtime` 是新增的判定，規則：該日期的列標記為即時，但列的 id 內嵌時間戳與所屬日期不符（TfL 與港鐵的路線檔都是這個形狀，id 形如 `2026-08-05-uk-tfl-2026-08-01T08:37:00-0`）。

### 二、覆蓋度計算（既有接縫，主要工作落點）

`src/data/stationCoverage.ts` 已經是「選單裡哪些站搜尋答得出來」的唯一模組，已產出 `StationCoverage` 經由 `/api/transit/stations` 送往 `StationBrowser`。**擴充它，不要另起爐灶。**

三項擴充：

1. **真實性過濾。** `coveredStationKeys()` 目前把所有路線的所有端點都算進來。改為只納入判定為 `scraped` 或 `realtime` 的日期切片的端點。
2. **日期感知。** 覆蓋度成為 `(country, date)` 的函式，而非只有 `country`。
3. **起點條件化可達集。** 新增一個查詢：給定 country、date、origin，回傳從該起點真的能抵達的站名集合。這是終點選單的資料來源。

`CoverageMode` 增加一個值，用來表達「此地區目前無可驗證班表」，讓前端能顯示說明與業者官方連結，而不是一個空選單。既有的 `catalog_only`（馬來西亞）已有此模式的先例——`/api/transit/lines` 回空陣列加 `message`——沿用同一套契約。

### 三、API 契約

- `GET /api/transit/stations` 增加選用參數 `date` 與 `origin`。帶 `origin` 時，回傳的 `stations` 即為可達集（終點選單）。`coverage` 物件增加一個欄位表達該國可查詢的日期範圍（`today_only` 或 7 天）。
- `GET /api/transit/lines` 只回傳有真實班表資料的線。無資料的國家回空陣列加 `message`，比照馬來西亞。
- `GET /api/transit/search` 在無結果時，回傳的訊息要能區分四種原因：路線不存在／該網路僅供當天查詢／該區無可驗證班表／該日期無班次。

### 四、跨線轉乘

**首爾（`searchSeoulSubwayArtifact`）：** 目前要求單一車次同時經過起訖站，因此完全沒有跨線轉乘。artifact 內有全部 12,314 個車次的完整停站序列（279 站、Line 1–9、平日／週六／週日假日三型），資料足以做真正的轉乘搜尋。實作為：找出經過起點的車次 → 在任一共同停靠站換乘 → 接上經過終點的車次，換乘等待需滿足該站的最短換乘時間。可達集在開機時依服務日類型預先計算三份（279 站的規模無效能疑慮）。

**通用鏈接（`findRoutePaths`）：** 目前只用路線檔的 `origin`／`destination` 作為圖的節點，完全不看 `stops`。因此真實換乘站若只出現在中途（港鐵荔景是荃灣線與東涌線的換乘站，但只存在於 `stops`）就永遠串不起來。**決定：把路線檔的中途停站也納入為可換乘節點。**

**最短換乘時間：** 目前的判定只有 `wait >= 2 && wait <= 120`，沒有任何車站層級的步行時間。兩分鐘在大型換乘站不成立。引進以車站為鍵的最短換乘時間，無資料時使用保守預設值。

**票價：** 鏈接結果目前把各段票價直接相加。單一路網內的轉乘（首爾、港鐵、新加坡）是一次計費，相加會高估。決定：跨營運商才相加，同營運商標記為「票價需向業者確認」而非給出錯誤數字。

**反向結果（`reverseResult`）：** 反向班次的時刻是由原方向的行車時間往前推算出來的，不是真實的反向班表。決定：保留此行為（否則反向查詢全滅），但結果需帶明確標記，且不得標示為即時。

### 五、Scraper 端修正

- `ProviderBackedScraper`：live adapter 只回傳少量「下班車」時，不得覆蓋當天既有的完整班表；改為合併或保留較完整者。
- 任何 provider 的即時快照**不得寫入非抓取當天的日期**。TfL 目前對七個日期各呼叫一次 API，取得的是七個相隔數分鐘的當下實況——這個迴圈本身是錯的。
- MBTA：修正週六重複累積（563 筆 vs 實際 144 筆），並調查平日末班被截斷在 16:58 的原因（疑似 API 分頁上限）。
- `scripts/lib/llmTransfer.ts`：目前驗證只要求「換乘站在站名清單內」與「總分鐘數 ±40%」，地理上錯誤的換乘站可以通過。決定：其輸出不得進入 committed 資料，或必須帶有來源標記使其被判定器歸類為非真實資料。

### 六、隱藏清單（套用上述規則後的結果）

| 網路 | 結果 | 依據 |
| --- | --- | --- |
| 首爾地鐵（279 站 / 9 線） | 保留，7 天 | 官方 CSV + sha256，服務日分型 |
| 波士頓 MBTA | 保留，7 天 | 真實排班，服務日正確（週日首班 06:15 vs 平日 05:30） |
| 倫敦 TfL | 保留，限當天 | 未來日期為 `stale_realtime` |
| 香港港鐵 | 保留，限當天 | 未來日期為 `indicative`；當天需先修覆蓋 bug |
| 新加坡 MRT | 隱藏 | 全部 `indicative`（109 筆固定班距、單一票價） |
| 曼谷 BTS/MRT | 隱藏 | 全部 `indicative` |
| 東京 Metro／都營 | 隱藏 | 程式內固定 10 分班距生成；且每條線只存 2 站 |
| 中／德／法／比／挪／瑞／馬 地鐵 | 隱藏 | 無地鐵資料 |

新加坡與泰國在 repo 內**只有**地鐵資料，因此這兩國會變成完全無結果。此為刻意取捨，已確認接受。國家保留在選單中並顯示無可驗證資料的說明與業者官方連結。

### 七、SEO 連帶影響

隱藏規則會讓 `scripts/generate-route-pages.ts` 少產生一批路線頁（新加坡與泰國共 8 條路線 × 6 語系 = 48 頁），已上線 URL 會變 404。依 CLAUDE.md，`npm run redirects` 不在 build 內，必須手動執行並提交。此為本 spec 的交付項目之一，不得遺漏。

## Testing Decisions

好的測試只驗證外部行為：給定一組路線快照與一個日期，覆蓋度計算應該回傳哪些站名；給定起點，可達集應該包含與排除哪些站。不驗證內部如何走訪、用了什麼資料結構。

**受測模組與現有前例：**

- **真實性判定器** — 新增測試檔。前例：`scripts/lib/routePages.ts` 的既有測試涵蓋 `isIndicativeTimetable`。測試以合成的路線快照為輸入（固定班距、混合班距、即時列、日期不符的即時列），驗證五種分類的邊界。
- **`src/data/stationCoverage.ts`** — 擴充既有的 `stationCoverage.test.ts`。驗證：`indicative` 路線的端點不出現在覆蓋集；起點條件化可達集在同線與跨線情況下的內容；日期改變時可達集隨服務日改變。
- **`src/data/scraped/timetableDay.ts`** — 擴充既有的 `timetableDay.test.ts`（純函式、無檔案系統，是理想的測試接縫）。驗證：中途停站可作為換乘節點（以港鐵荔景的形狀為案例）；最短換乘時間被遵守；同營運商鏈接不重複計費。
- **首爾轉乘** — 擴充既有的 `src/data/scraped/seoulArtifactSearch.test.ts`。驗證跨線站對（江南→首爾站）回傳結果、換乘站正確、服務日切換正確。
- **API 契約** — 前例：`src/server/providerStationResolution.test.ts`。驗證 `origin` 與 `date` 參數對 `/api/transit/stations` 回傳內容的影響，以及四種無結果原因的訊息區分。

**服務日測試的既有陷阱：** 依 CLAUDE.md，任何新的 service-day 測試套件必須使用 `serviceDayArtifactFixture()`（`src/server/serviceDayArtifactFixture.ts`）來暫存與還原被追蹤的 artifact 檔，否則會弄髒工作目錄，且套件只有在前一次執行已刪除檔案的情況下才會通過。

`npm run lint`（`tsc --noEmit` + `vitest run`）是每次變更的關卡。

## Out of Scope

- **接上新的資料源。** 是否要接 ODPT（東京地鐵）、SMRT、BEM 等，屬於 `METRO_DATA_SOURCE_AUDIT.md` 的範疇，不在本 spec。本 spec 只處理「現有資料要怎麼誠實呈現」。
- **補齊被隱藏網路的班表資料。** 讓新加坡與曼谷重新出現，需要真實資料源，那是另一個工作。
- **高鐵與城際路線的資料真實性。** 轉乘邏輯的修正會連帶影響它們（`findInRoutes` 是全國共用），但本 spec 不稽核也不改變日／韓／中／德／法／比／挪／瑞的高鐵資料呈現。
- **重繪路線圖 UI。** 本 spec 只決定哪些線出現，不改變它們如何被繪製。
- **馬來西亞。** 本來就是 `catalog_only`，行為不變。
- **稽核報告本身。** `METRO_TRANSFER_AND_INTEGRITY_AUDIT.md` 先於本 spec 產出，是本 spec 隱藏清單的輸入來源。

## Further Notes

- 這個 repo 已經有一半的正確答案了。`isIndicativeTimetable()` 的註解明白寫著把捏造的發車時刻當作 schema.org 結構化資料輸出等於餵給所有信任它的下游；`stationCoverage.ts` 的檔頭註解明白寫著選單與時刻表是兩張不同的圖，因此會 404。兩個判斷都對，只是**只套用在 SEO，沒有套用在 App**。本 spec 的核心是把既有的正確判斷擴展到使用者實際看到的地方，而不是發明新東西。
- 隱藏規則生效後，整個 App 的地鐵功能實質上只剩首爾（279 站、完整）與波士頓（4 條線、需修截斷）。這個結果看起來很少，但它是誠實的下界。此前的「豐富」有相當比例是生成出來的。
